# deploy/ 单机部署骨架

> **F-57 状态：`HISTORICAL_LINUX_RESEARCH_ONLY`。** 本目录的 systemd、cgroup、Podman、Docker Compose、`/var/lib/ep` 和 64GiB 预算不得用于正式生产，也不得被描述为 Windows Server 2022 安装入口。现行生产规范见 [F-57 Windows/P340 生产档案](../docs/superpowers/specs/2026-08-23-f57-windows-p340-production-profile.md)。目录暂保留用于旧决策追溯和开发研究，不执行其中生产命令。

本目录当前只有交付物 D-06 的一部分：`systemd/system/` 下八个 cgroup slice 的静态资源限额 drop-in。
八个 slice 单元本身、Podman Quadlet 与 Docker Compose 两套等价编排文件属交付物 D-05，不在本文件范围内。

判定方是 `scripts/verify-resource-limits.sh`，在部署与升级时各执行一次。
本目录不含配额生成器，也不产出 `quotas.generated.toml`；任何进程的启动自检中都没有资源限额项。

## 一、八行与八个 slice 的对应

规格第 13.1 章的配额表共九行，其中八行有独立 slice，逐行落一个 drop-in。
对应关系取自技术基线第 2 节，不另行指派。

| 规格行 | 行名 | CPU 份额 | 内存上限 | 磁盘 IO 份额 | slice | 承载进程 |
|---|---|---|---|---|---|---|
| 1 | PostgreSQL 16 | 44% | 48% | 50% | `app-db.slice` | PostgreSQL 16 |
| 2 | Rust 核心与集成网关 | 20% | 16% | 11% | `app-core.slice` | core-server、integration-gateway |
| 3 | Worker | 10% | 8% | 8% | `app-worker.slice` | job-worker |
| 4 | 内置搜索索引 | 10% | 10% | 8% | 无 | 无独立进程，见偏差一 |
| 5 | 插件运行时 | 5% | 5% | 4% | `app-plugin.slice` | plugin-host |
| 6 | 反向代理与运维代理 | 3% | 2% | 2% | `app-edge.slice` | 反向代理、ops-agent |
| 7 | 公网门户 | 3% | 3% | 1% | `app-portal.slice` | portal-gateway |
| 8 | 连续归档、附件增量与审计证据写出 | 2% | 3% | 6% | `app-archive.slice` | archive-writer |
| 9 | 全量备份、附件存量搬运与备份校验 | 3% | 5% | 10% | `app-backup.slice` | backup-writer |

## 二、四类取值的口径

第一类与第二类是两个权重列，逐行取该行百分数乘以 100，与机器规格无关，不参与任何折算，
换机型时一个数都不改。它们只表达八个 slice 之间的相对比例，不表示该 slice 取得整机的对应百分比：
同机的 `system.slice` 与规格该章的操作系统预留不在这八行内，权重之和不构成整机分母。

第三类是内存的保底与上限，同值，绝对字节。算定式如下，八行同批适用：

```
可分配量 = 服务器总内存 × (1 − 操作系统预留 5%)
该行 MemoryMax = MemoryLow = floor(可分配量 × 该行内存百分数 ÷ 1 MiB) × 1 MiB
```

当前取值按总内存 64 GiB 算定，即可分配量 62259.2 MiB：

| slice | 内存百分数 | MiB | 字节 |
|---|---|---|---|
| `app-db` | 48% | 29884 | 31335645184 |
| `app-core` | 16% | 9961 | 10444865536 |
| `app-worker` | 8% | 4980 | 5221908480 |
| `app-plugin` | 5% | 3112 | 3263168512 |
| `app-edge` | 2% | 1245 | 1305477120 |
| `app-portal` | 3% | 1867 | 1957691392 |
| `app-archive` | 3% | 1867 | 1957691392 |
| `app-backup` | 5% | 3112 | 3263168512 |

第四类是 `app-backup.slice` 的磁盘 IO 硬上限，200 MiB/s，设备按 `/var/lib/ep` 所在块设备解析。
它压住每晚的全量窗口，是八行中唯一的硬上限，理由是磁盘 IO 是本机唯一真实稀缺的一维，
而权重只在竞争时收敛，压不住业务空闲时段备份把设备吃满、进而抬高备份窗口内交易时延的情形。

客户服务器规格不低于附录 A.4 认证报告所记规格时沿用该次认证结论、不重跑 A.4；
两个权重列原样沿用，三个绝对值由实施方按上述同一算定式对全部八行同批重算并写入部署记录，
不得单独调高任一行。低于该下限的服务器不交付。

## 三、两处已披露的偏差，不以加和或拆分掩盖

**偏差一：八行权重之和低于满值。** 配额表第 4 行「内置搜索索引」在首版既无独立进程也无独立 slice，
其检索与索引写入分别落在 core-server 与 job-worker 之内。该行份额不落 drop-in、不加和到任何一行、
也不按比例拆分到多行，因此八行 `CPUWeight` 之和为 9000、`IOWeight` 之和为 9200，均低于满值 10000。
cgroup v2 按参与竞争的权重之和归一化分配，分母缩小意味着实际承载搜索负载的 `app-core.slice` 与
`app-worker.slice` 相对规格意图欠配，其余六个 slice 相对超配。该偏差按附录 A.4 实测记录，首版不消除，
待搜索索引具备独立进程与独立 slice 时按同一口径一次补齐。内存列是硬上限不是权重，第 4 行不落值
只在可分配量中留下约一成未指派余量，不构成对其余八行的相对超配。

校验脚本把 9000 与 9200 两个和值写死并逐次断言，理由是有人把缺口悄悄补平时必须被检出。

**偏差二：突发上限一列在首版无承载。** 规格第 13.1 章「其余各行的突发上限取其份额的三倍并以
可分配量的 40% 封顶」一句在首版没有对应取值，drop-in 不设 CPU 与磁盘 IO 的突发上限。
`app-backup.slice` 的硬上限是压住每晚备份窗口的手段，不是该列的实现。该列属未落实项，不是已覆盖项。
对公网门户而言，这意味着资源侧遏制只覆盖内存一维与两个权重份额：其余 slice 空闲时，
被攻破或遭洪泛的门户进程仍可短时借用整机空闲的 CPU 与磁盘 IO。交付材料不得表述为已覆盖。

校验脚本为此断言四类取值之外的键一律不出现，有人补一个 `CPUQuota` 或 `MemoryHigh` 上去即判不符。

## 四、三处文档未给出、由本次交付暂取的值

以下三处在规格、技术基线、阶段计划与裁定登记中均无取值，落码时不得不选定。三处都不是判据，
校验脚本不把它们与配额表比对，但它们进了交付物，须在认证冻结前复核。

1. **PostgreSQL 一行的 slice 名。** 技术基线第 2 节的进程表只给出八个进程的七个 `app-*.slice`，
   第八个 slice 即 PostgreSQL 的那个从未命名。本次按同一形态取 `app-db.slice`，不新增命名机制。
2. **BC-1 的服务器总内存。** 附录 D.2 的 BC-1 只固定 CPU 架构、操作系统、数据库与编排四项，
   不含内存容量；附录 A.4 把服务器规格交给认证报告记录，而该报告尚不存在。因此「按 BC-1 算定的
   绝对字节」今天算不出唯一解。本次按总内存 64 GiB 暂取并写明算定式，认证冻结后按同一式子同批重算。
3. **磁盘 IO 硬上限的数值与其承载指令。** 数值 200 MiB/s 无文档来源，按 A.3 的附件正文全量约 800 GB
   在一个夜间窗口内写完反推，暂取。承载指令方面，systemd 没有名为 `IOMax=` 的指令，
   cgroup v2 的 `io.max` 由 `IOReadBandwidthMax=` 与 `IOWriteBandwidthMax=` 承载，二者各需一个设备路径，
   且把计划所称的「一个 MB/s 数字」拆成读写两个键。本次两个方向取同一设备、同一数值，
   校验脚本断言这一点，使「一个数字」这一口径仍可判。设备锚点 `/var/lib/ep` 取自技术基线第 2 节。

## 五、校验脚本

```
scripts/verify-resource-limits.sh [--self-check | --runtime | --all]
```

- `--self-check` 只做 drop-in 自洽性：两个权重列与规格第 13.1 章该行百分数乘以 100 逐行整数相等，
  内存两列同值且为正整数字节，硬上限读写两行同设备同值，八行齐备、无第九行、无越界的键。
  这一半不读 cgroup，在没有 cgroup 的开发机上同样可判。
- `--runtime` 只做运行期比对：读 cgroup v2 目录下的 `cpu.weight`、`io.weight`、`memory.low`、
  `memory.max` 与 `io.max`，与 drop-in 逐行比对。
- `--all` 为默认，两半都做。部署与升级时各执行一次即取此模式。

退出码分三种，不合并：

| 退出码 | 含义 |
|---|---|
| 0 | 通过 |
| 2 | 取值不符 |
| 3 | 被测对象读不到，判定未做出 |
| 64 | 用法错误 |

**读不到 cgroup 时退出码是 3 而不是 0。** 未覆盖不是通过：没有 cgroup 的机器上运行期那一半
一行都没有比过，脚本据此不判通过，只报未覆盖。同一次运行里既有不符又有未覆盖时取 2。

`EP_DROPIN_ROOT`、`EP_CGROUP_ROOT` 与 `EP_IOMAX_DEVNO` 三个环境变量只为负样例存在，
不设时一律取仓库与本机的真实路径；后两个一旦设置，脚本在输出里明写本次比对用的是替代值。
