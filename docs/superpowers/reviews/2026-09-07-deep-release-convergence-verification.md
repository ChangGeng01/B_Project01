## 容量与连接口径

四个应用池为 `rw=20 / ro=10 / worker=5 / ops=2`，常驻总计 37；加临时 10 和应用内安全量 5 得到峰值 52。PostgreSQL 普通连接容量为 `64-4-3=57`，再减应用峰值 52，剩余普通槽位为 5。这两个 5 的含义不同；不得混入 F-57 其他认证预算。

当前已安装的 1 TB HDD 永久 `production_eligible=false`，不能通过认证变成生产权威盘、RAID1 成员或备份目标。新生产数据盘要求原始容量至少 `2,000,000,000,000` bytes，并满足：

```text
九桶合计 = 1,481,763,717,120 bytes
不可借用预留 = 107,374,182,400 bytes
名义 NTFS 下限 = 1,589,137,899,520 bytes
实际 NTFS 下限 = max(名义下限, 九桶合计 + 预留 + measured_unclassifiable_filesystem_allocation_bytes)
共享桶合计 = 64,424,509,440 bytes
```

公式中的实测项只允许已证明属于 NTFS / BitLocker 元数据的分配量，不是未知文件或业务数据的兜底桶；`unclassified_allocation_bytes` 必须为零。这里只核对规格与算术；没有读取或认证用户的 P340 磁盘。

WAL 修正保持九桶、十四类、十四个选择器和全部容量数值不变；补充的是合法对象及生命周期证明，包括未来循环复用段、归档状态和 Windows 删除瞬态。未知名称、未知生命周期和重复归属仍拒绝。依据为 [PostgreSQL 16 WAL 文档](https://www.postgresql.org/docs/16/wal-configuration.html) 与 [官方 WAL 源码](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/access/transam/xlog.c)；采集器、原因台账及规划正负样例本身仍未实现或执行。
