# 首版范围收窄决策(产品负责人已确认)

> **历史范围依据，不是现行实现规格。** 本文保留首轮范围收窄的批准记录；其“高可用”等早期取值随后被单服务器决策覆盖，平台、财务、内部技术阻断与运维发布又分别由现行总体规格、F-50、F-51、F-52、F-53 继续收口。开发时不得直接从本文提取架构、计数、状态机或验收值；它只证明某项为何纳入或延期。

来源:客户提供的收束版需求《管理软件基本需求.docx》,原文见 scope_requirements.txt。
基本规则:**收束版未收录的功能一律 defer**,但受下列四条口径约束。

## 口径一:平台与架构按"中间档"处理

保留:私有化部署、法人与字段级权限、低代码定制、白标、四端客户端、审计、
高可用、备份恢复、数据迁移、等级保护参考目标。

defer:本地 AI/OCR、MCP、向量检索与知识图谱、RAG、流程挖掘/预测/优化/仿真、
边缘节点断网运行、工业接入与 IoT/数字孪生、五数据库认证矩阵(首版只认证
PostgreSQL,其余四种 defer)、国密与商用密码密评档位。

## 口径二:轻量保留

收束版正文顺带提到但无独立章节的能力,保留到"刚好满足收束版原文所需"的深度:
库存台账与可用量查询、客户信用额度校验(现规格缺失,需新增)、项目任务、
批次与设备档案及保修。

defer:完整 WMS(波次、拣货、盘点、质检、预留、调拨)、MES 与三类制造、
PPM 挣值与资源工时、EAM 点检维修可靠性。

## 口径三:闭环优先(**最高优先级,与口径一二冲突时以本条为准**)

首版必须在应用内跑通完整闭环,不依赖外部系统或人工台账:

> 销售建单 → 合同审批 → 发票申请 → 采购订货/付款申请 →
> 财务开票/到款/付款登记 → 工单 → 管理层查看收入、成本、交付、利润

因此即便收束版字面未列,凡闭环所必需的最小能力一律保留,包括但不限于:

- 应收与应付台账(支撑到款登记、付款登记与账龄)
- 简易总账(科目、凭证、期间结账;支撑收入与利润口径)
- 存货计价与成本归集(支撑"成本"与"利润";与库存台账同层,不含完整成本管理)
- 基础经营报表与管理驾驶舱(收入、成本、交付、利润;收束版"报表"小节的落点)
- 发票开具的应用内闭环(开票记录、号码、金额、比例、与收款计划勾稽)

**判定原则**:"未收录即 defer"是手段,"应用内闭环"是目的;冲突时手段服从目的。
任何会导致闭环断点、迫使用户切换到外部系统或人工处理的 defer,一律不成立。

保留的最小能力必须写明边界,避免借闭环之名把完整模块带回首版。

## 口径四:外部主系统替换能力大幅收窄

现规格要求每个模块都具备外部主系统替换能力(附录 B,GA 硬门禁),在"应用内闭环"
定位下等于每个模块做两遍,性价比不成立。

首版只对**电子签章一类**保留外部对接与替换能力,其余模块的外部主系统替换能力全部
defer,附录 B 相应收窄。

**变更记录(2026-08-04)**:本条初稿为"银行、税务、电子签章三类"。该取值是在闭环
走查之前确定的,当时假设这三类都为闭环所必需。随后按口径三的闭环推演表明:收束版
要求的到款登记、付款登记均为人工登记口径,发票开具为应用内登记,闭环不依赖银企直连、
自动对账或税务平台在线对接。据此收窄为电子签章一类,银行与税务侧的外部对接与替换
能力全部延期。规格第 2.2、2.3、4.2、5.6、5.7、10.2、10.4、20、22 章与附录 B 均按
一类执行。

## 延期项的记录要求

被 defer 的内容不得直接删除,须集中登记为"延期目录",逐条保留原条目名称,
并注明延期理由(收束版未收录 / 口径一 / 口径二 / 口径四),以便后续版本恢复。
