# ADR-0010 迁移窗口并发开窗以单例锁表串行化

- 状态：已接受
- 出处：阶段 2 计划第 3.5 节表六；迁移 V20260901093500

## 背景

迁移窗口的不变量是「同一时刻至多一个 OPEN 窗口」。并发开窗若不加串行化，两个事务各自读不到 OPEN 行、各自插入，不变量即被破坏。常规做法是对 `migration_windows` 建部分唯一索引 `where state = 'OPEN'`，但基线第 3.10 节禁止部分索引。

## 决定

新增单例锁表 `platform_core.migration_window_lock`：只有 `id smallint` 一列，`check (id = 1)` 固定一行，建表迁移同时插入该行，`db/checks/01` 对该表豁免公共列要求。开窗流程在同一事务内先对该行取 `SELECT ... FOR UPDATE`，再读 `migration_windows` 判定无 OPEN 行，然后插入新窗口；关窗同样经该行串行化。锁表自身不参与任何业务读写，只作锁的载体。

## 理由

选「单例锁表加行锁」而不是「应用层分布式锁或排队服务」：不采用本决定的代价是引入第二个协调点。单机形态下没有独立的锁服务，自建一个即新增进程与故障面；而数据库行锁是本部署形态里已经存在、且与窗口数据同处一个事务内的唯一协调机制，串行化判定与窗口插入同事务提交，不存在锁判定与数据写入之间的间隙。

选「锁表而非部分唯一索引」：部分索引被基线禁止，绕行它等于推翻一条冻结约定，代价由全部建表阶段分担；锁表的代价只是多一张一行表与一处 check 豁免。

## 后果

正面：不变量在数据库层强制，双开窗的败方在行锁上等待或直接以冲突退出，无应用层判重代码；A-09 开窗端点的并发语义即由此表承载。

负面（如实记录）：所有开窗、关窗操作串行在同一行锁上，窗口操作本身是低频人工操作，该串行化不构成吞吐瓶颈；若未来窗口操作高频化，本决定需重新评估。锁表行不可删，删行会使判窗守卫视同窗口关闭、开窗流程以锁行缺失失败，两种行为均已在仓储层登记。

## 影响范围

- `db/migrations/platform_core/V20260901093500__platform_core_migration_windows.sql`；
- `crates/adapter/db-pg` 的迁移窗口仓储开窗/关窗路径；
- `docs/data-dictionary.md` 第 6 节该表条目与 `db/checks/01` 豁免登记。
