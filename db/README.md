# `db/` 数据库侧目录

本目录不是 Cargo workspace 成员。它与 `/scripts/`、`/deploy/`、`/clients/desktop/`、`/clients/mobile/`
同属技术基线第 1.1 节第二段列出的非 workspace 成员顶层目录，新增顶层目录必须先改基线第 1.1 节。

## 三个子目录的分工

| 目录 | 承载物 | 由谁执行 | 内容交付阶段 |
|---|---|---|---|
| `bootstrap/` | 集群引导，簇级对象与实例参数 | 超级用户手工执行，不走迁移 | 阶段 2 |
| `migrations/` | 每 schema 一个迁移目录 | `ep-migrate apply`，单一全局 Runner | 阶段 2 起逐阶段追加 |
| `checks/` | SQL 合规断言脚本 | 编号脚本由 `ep-migrate check` 执行；`append_only_consistency.sql` 由 `xtask sqlcheck` 执行 | 阶段 2 |

`bootstrap/` 单独成路径而不并入迁移，理由是角色与集群参数是簇级对象，而 `ep_migrator` 按技术基线
第 3.1 节不具备角色管理权限，迁移路径在权限上根本执行不了这些语句。

## 阶段 1 在本目录下交付了什么

只有约定，没有任何可执行内容：

- `bootstrap/README.md` 记下五个引导文件名与其执行顺序，五个文件本身只含说明性注释。
- `migrations/` 下 24 个空目录，目录名与技术基线第 3.1 节的 24 个 schema 名一一对应。
- `checks/README.md` 记下该目录的归属，脚本本身归阶段 2。

全仓在阶段 1 结束时不存在任何会真正建库、建角色、建表或改实例参数的语句。

## 24 个空目录如何进版本库

Git 不跟踪空目录，因此每个 schema 目录下放一个零字节的 `.gitkeep`。取 `.gitkeep` 而不取
`README.md` 或 `.gitignore`，理由是它零字节、无内容、不承载任何语义，因此不可能被读成顺序声明；
换成带正文的占位文件就得逐个说明它不表达先后，反而给「目录只表达归属不表达先后」这条约定开了解释口。

阶段 1 退出条件第 5 条要求「24 个空目录存在，且目录中不含任何顺序声明文件」。此处「空」取
「不含任何迁移文件与任何顺序声明文件」之义：字面意义上的空目录在 Git 中无法存在，按字面读会使这条
退出条件在任何克隆出来的工作副本上恒不可满足。`.gitkeep` 不是顺序声明文件，落在这条约定之内。

对应地，`xtask sqlcheck` 判定 `db/migrations/` 时的判据必须是「该目录下不出现顺序声明文件」，
而不是「目录条目数为零」。

## 迁移执行顺序

执行顺序由阶段 2 交付的单一全局 Runner 按文件版本号全序排定。目录只表达归属，不表达先后。
按裁定，`db/migrations/` 下的顺序声明文件整类撤销，任何阶段不得重新引入。
