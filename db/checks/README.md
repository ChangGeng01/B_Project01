# `db/checks/` SQL 合规断言脚本

本目录是技术基线第 1.1 节第二段固定的顶层目录之一。

## 阶段 1 在本目录下交付了什么

只有本文件，**没有任何断言脚本**。

脚本本体是阶段 2 交付物 D-04：13 个编号断言脚本加一个不编号的 `append_only_consistency.sql`，
阶段 2 计划第 3 节是其唯一出处。阶段 1 交付物 D-04 只覆盖 `db/bootstrap/` 的目录与执行顺序约定
以及 `db/migrations/` 的目录骨架，不含本目录的任何脚本。

阶段 1 退出条件第 11 条点名的十项规则是 `xtask sqlcheck` 的**静态**检查规则，被检对象是仓库里的
SQL 文本；本目录的脚本是在**活库**上执行的断言，被测对象是 `pg_catalog` 与
`information_schema` 中的实际对象。两者判据不同、执行时机不同、承载方也不同，
不得把退出条件 11 读成对本目录的要求。

## 两条执行路径

| 脚本 | 执行方 | 通过判据 |
|---|---|---|
| 01 至 13 号编号脚本 | `ep-migrate check` | 每脚本返回 0 行 |
| `append_only_consistency.sql` | `xtask sqlcheck` | 返回 0 行 |

不编号的那一个不计入 `ep-migrate check` 的十三项。两条路径分开，是因为编号脚本断言的是迁移刚落成的
物理结构、须在迁移窗口内随迁移一并判定，而仅追加登记与触发器的一致性要在登记行由多个阶段陆续补齐
之后持续兜底，跟单次迁移窗口不同步。

## 阶段 1 不在本目录建空文件的理由

编号脚本的编号与其断言内容一一绑定（01 公共列齐备、02 行级安全已启用且强制，依此类推）。
先建 13 个空文件占位，等于在没有任何被断言对象的阶段就把编号钉死，且空脚本执行时返回 0 行，
与「断言通过」在返回值上无法区分——这正是一条静默返回成功的路径。因此本阶段只留本文件。
